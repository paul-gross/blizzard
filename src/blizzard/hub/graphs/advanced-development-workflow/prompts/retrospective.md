# Retrospective (advanced-development-workflow)

You are working a chunk's **retrospective** node-step — deliver *reported* the work landed (every repo merged into its base branch), and this node is the last one standing at the last trust boundary before the chunk closes, so it re-derives that report rather than taking it on faith. Read the chunk's own journey with `blizzard runner chunk history` — the transitions, migrations, and bounces it took to get here, oldest-first, including any bounced attempt that produced no artifact — then review its findings content through the envelope's asset trail: above all each node's own `retrospective` asset, the per-node diary you are synthesizing, plus the plan, the plan-review and review findings, the verification report, and the pre-push summary.

**Verify the landing before writing anything.** Start from the `delivery-findings` artifact when one exists — `blizzard runner artifact get delivery-findings --node deliver --content`, the same diagnosis input `resolve.md` reads — instead of re-deriving from nothing. Check, per repo (`blizzard runner artifact list` for the declared `git_commit` pointers):

1. every declared commit's sha is reachable from that repo's base branch — `git merge-base --is-ancestor <sha> origin/<base>` in the repo's own worktree, exit 0 means reachable;
2. that repo's PR is merged — `gh pr view` from inside the worktree;
3. the chunk's originating work item is closed — reread it via `blizzard runner work-items <chunk-id>`.

Record the result in the retrospective asset's **Landing Verification** section regardless of outcome — a clean landing states that it checked out clean, not just that it landed. If any leg fails (a declared sha not reachable from base, or a repo's PR unmerged), do not repair it here and do not write the closing reflection yet — your judgement takes `delivery-incomplete` instead, naming the specific discrepancy (see `retrospective.judgement.md` for exactly when this applies and its loop bound); the retrospective is written once the chunk returns here with the discrepancy repaired.

Separately, check whether the landing turned the base branch's own gate red: `gh run list --commit <merge-sha>` per repo, using the PR's merge commit (`gh pr view --json mergeCommit`). This is never a reason to route backward — the code is on base and stays there — but a completed red run is a real finding: record it in the retrospective asset and file a follow-up issue for it as its disposition, using the filing convention [../docket.md](../docket.md) already owns (the workspace's own issue-filing convention if it declares one, otherwise `gh issue create` from inside that repo's worktree).

Before you write the retrospective, fold the chunk's findings docket per [../docket.md](../docket.md): enumerate every id in the newest `plan-findings` asset and the newest `review-findings` asset (either may be an empty list — a clean gate or a clean review passed with nothing to record), match each against the disposition records recorded across the chunk's node `retrospective` assets, and for every `should-fix` id left unmatched, file a forge issue for it — follow the workspace's own issue-filing convention if it declares one, otherwise run `gh issue create` from inside that finding's own repo worktree (its anchor names the repo) so `gh` targets the right forge — and record that filing as its disposition. An unmatched `blocking` id shouldn't occur; if one does, file it the same way and flag the anomaly.

Submit the retrospective as this node's `retrospective` asset before you declare done: run `blizzard runner artifact create --name retrospective` with the content on stdin, with these sections: **Landing Verification** — the three-leg check above and the merge-commit gate check, on every landing, clean or not; **What Went Well**; **What Didn't Go Well**; **Harness / Context Improvements** — concrete, actionable changes to the harness, tooling, agent docs, or conventions that would make the next run faster, more accurate, or more autonomous (this section is the point of the retrospective); **What We Skipped** — untested paths, deferred work, known gaps; **Findings Docket** — the fold table (id, source, severity, anchor, disposition, reference), or its absence noted if the chunk had no plan-findings or review-findings to fold. Keep it honest and specific; name files and findings, not vibes. Do not change the delivered code from this node.

Then, **after the asset is submitted**, carry out whatever **post-delivery** work this workspace asks of the node. Read the workspace's own agent context for a post-delivery convention: a workspace that declares one — redeploying the landed build, publishing an artifact, notifying something downstream — expects this node to honor it, and a workspace that declares none leaves this node at the reflection above. The asset goes first so a reflection already recorded survives whatever the post-delivery work costs; follow the workspace's convention for the rest, including any warning it gives about how that work behaves.
