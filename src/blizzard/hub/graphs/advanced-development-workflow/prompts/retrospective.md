# Retrospective (advanced-development-workflow)

You are working a chunk's **retrospective** node-step — deliver *reported* the work landed (every repo merged into its base branch), and this node is the last one standing at the last trust boundary before the chunk closes, so it re-derives that report rather than taking it on faith. Read the chunk's own journey with `blizzard runner chunk history` — the transitions, migrations, and bounces it took to get here, oldest-first, including any bounced attempt that produced no artifact — then review its findings content through the envelope's asset trail: above all each node's own `retrospective` asset, the per-node diary you are synthesizing, plus the plan, the plan-review and review findings, the verification report, and the pre-push summary.

**Verify the landing before writing anything.** Start from the `delivery-findings` artifact when one exists — `blizzard runner artifact get delivery-findings --node deliver --content`, the same diagnosis input `resolve.md` reads — instead of re-deriving from nothing. In each repo's own worktree, `git fetch origin` first — the worktree's `origin/<base>` was last refreshed when the environment was acquired, never since, while the merge itself happened on the forge, not in this worktree — then check:

1. **the landed sha is reachable from base.** `blizzard runner artifact list` returns one `git_commit` entry per repo per node that declared one — `build`, and `pre-push` or `resolve` again if either rewrote the branch — so take the **newest `epoch`** entry per repo, the same "latest wins" rule delivery itself uses when it lands (`hub/delivery/hub_node.py::_latest_commit_per_repo`); an older, superseded declaration for that repo is expected to be unreachable after a rewrite and is not a discrepancy. `git merge-base --is-ancestor <sha> origin/<base>` (`origin/master` unless the repo records another, same as `pre-push.md`) in that repo's own worktree, exit 0 means reachable;
2. **that repo's PR is merged** — `gh pr view` from inside the worktree;
3. **the chunk's originating work item is closed** — `blizzard runner work-items <chunk-id>` gives you each work ref's `web_url`; the work item itself carries no closed/open field, so ask the forge directly: `gh issue view <web_url> --json state -q .state` returns `CLOSED`/`OPEN`. A forge-side "closes on merge" convention is opportunistic, never guaranteed (some sources honor no such convention at all), so an open item here is recorded as a finding — never on its own a reason to select `delivery-incomplete`; only legs 1 and 2 are (see `retrospective.judgement.md`).

Record the result in the retrospective asset's **Landing Verification** section regardless of outcome — a clean landing states that it checked out clean, not just that it landed. If leg 1 or leg 2 fails for any repo (that repo's newest declared sha not reachable from base, or its PR unmerged), submit the retrospective asset now with the **Landing Verification** section naming the specific discrepancy — the remaining sections can wait, they belong to the visit that actually closes the chunk — and your judgement takes `delivery-incomplete` instead of `recorded` (see `retrospective.judgement.md` for exactly when this applies and its loop bound).

Separately, check whether the landing turned the base branch's own gate red: `gh run list --commit <merge-sha>` per repo, using the PR's merge commit (`gh pr view --json mergeCommit`). This is never a reason to route backward — the code is on base and stays there — but a completed red run is a real finding: record it in the retrospective asset and file a follow-up issue for it as its disposition, using the filing convention [../docket.md](../docket.md) already owns (the workspace's own issue-filing convention if it declares one, otherwise `gh issue create` from inside that repo's worktree).

Before you write the closing reflection, fold the chunk's findings docket per [../docket.md](../docket.md): enumerate every id in the newest `plan-findings` asset and the newest `review-findings` asset (either may be an empty list — a clean gate or a clean review passed with nothing to record), match each against the disposition records recorded across the chunk's node `retrospective` assets, and for every `should-fix` id left unmatched, file a forge issue for it — follow the workspace's own issue-filing convention if it declares one, otherwise run `gh issue create` from inside that finding's own repo worktree (its anchor names the repo) so `gh` targets the right forge — and record that filing as its disposition. An unmatched `blocking` id shouldn't occur; if one does, file it the same way and flag the anomaly.

Submit the retrospective as this node's `retrospective` asset before you declare done, on **every** visit including a discrepancy one — the node's `produces: [retrospective]` covers each attempt, not only the one that closes the chunk: run `blizzard runner artifact create --name retrospective` with the content on stdin. On a clean landing, or once a chunk returns here with a prior discrepancy repaired, write the full asset: **Landing Verification** — the three-leg check above and the merge-commit gate check; **What Went Well**; **What Didn't Go Well**; **Harness / Context Improvements** — concrete, actionable changes to the harness, tooling, agent docs, or conventions that would make the next run faster, more accurate, or more autonomous (this section is the point of the retrospective); **What We Skipped** — untested paths, deferred work, known gaps; **Findings Docket** — the fold table (id, source, severity, anchor, disposition, reference), or its absence noted if the chunk had no plan-findings or review-findings to fold. On a discrepancy visit (your judgement selects `delivery-incomplete`), the asset needs only **Landing Verification**, naming the specific discrepancy — the other sections are written on the visit that actually closes the chunk. Keep it honest and specific; name files and findings, not vibes. Do not change the delivered code from this node.

Then, **only on the visit that writes the full closing reflection** (never on a discrepancy visit — the landing is not actually complete yet, and post-delivery work assumes it is), and **after the asset is submitted**, carry out whatever **post-delivery** work this workspace asks of the node. Read the workspace's own agent context for a post-delivery convention: a workspace that declares one — redeploying the landed build, publishing an artifact, notifying something downstream — expects this node to honor it, and a workspace that declares none leaves this node at the reflection above. The asset goes first so a reflection already recorded survives whatever the post-delivery work costs; follow the workspace's convention for the rest, including any warning it gives about how that work behaves.
