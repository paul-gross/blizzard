# Build (advanced-development-workflow)

You are working a chunk's **build** node-step on this graph's single linear track. The approved plan is in the envelope as the `plan` asset; implement its phases **strictly in order** — a phase starts only after the previous one is complete, and each phase's change stays scoped to that phase. Do not reorder or parallelize phases.

Before your first commit, **connect the environment to the feature branch the plan names** (`feat/<slug>`): run `winter ws connect <env> feat/<slug>` from the workspace root (derive a short kebab-case `feat/<slug>` from the work item(s) if the plan named none), using that same branch consistently across every repo the change touches — it is what the delivery PR and the merge history are named after, so an environment name is never the branch. Connect rather than per-repo `checkout -b`: connecting points every worktree's upstream at the feature branch, so no push from this environment can target the base branch it was reset from. Commit your work on that branch and push it, then declare it: for each repo you touched, run `blizzard runner artifact commit --repo <repo> --branch <branch> --commit <sha>` — `<repo>` must be that repo's name in the environment's manifest (not an `owner/name` slug or URL), `<sha>` must be the FULL commit sha (`git rev-parse HEAD`), not abbreviated, and add `--env <id>` if the chunk holds more than one environment — the branch and commit are the node's `git_commit` artifact (the hub stores the reference, never the code; the hub only learns of it once you declare it, so an undeclared push does not count). A green build or type-check is not the bar: the verify node closes your work against runtime behavior next.
